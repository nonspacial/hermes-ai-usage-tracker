# Period-change latency: measured read-side cost

**Scope:** `ee941c4` baseline and an uninstalled candidate. Measurements are local read-only copies of the default and `infra` usage ledgers, or disposable synthetic fixtures. They do not prove end-to-end gateway/browser latency, concurrency under load or another user's profile. The **Online** badge denotes recorder/subscription health, not a fast analytics response (`ANALYTICS_RELOAD.md`). No provider/account endpoint or live-ledger writer was called.

## Exact backend incremental candidate (repository-only, later than the renderer-cache investigation)

A newly created synthetic ledger now installs transactional change triggers; a projected selected-profile Overview/time **or model** snapshot pairs its SQL data with a SQLite revision, durable DB identity, source-file generation and bounded signed resume token. `POST /ledger/refresh` accepts unchanged bounds or a forward-moving 24h window (up to one hour), re-reads affected and clipped edge buckets plus session-stream successors, then recomputes exact shared header/provider/model/subagent totals and scoped distinct counts. Both selected GET and refresh use disposable SQLite snapshots, including a live WAL, rather than source-dir `mode=ro` sidecars. Unsupported views/changes, old ledgers, gaps or >128 journal mutations, oversized old/new row images, altered project metadata, catalog/health/context/reconciliation writes, open owners, >4 buckets or >2048 rows in an affected bucket, and concurrent commits/replacements use full reads or require fresh GET. The earlier section's “until implemented” and “no migration introduced” describe the **renderer-only predecessor**; they do not describe this source candidate. Existing ledgers are **not** auto-migrated, so installed performance on the copied/real older ledger is unchanged. The frontend integration is described in [the later frontend section](#frontend-incremental-consumption-repository-only-after-backend-independent-review). See [the typed endpoint/storage contract](INCREMENTAL_ANALYTICS_CONTRACT.md) for journal retention, memory and integration details.

A fixed disposable **6,000-request** fixture (40 sessions, fixed timestamps, no provider traffic) was run with `.venv/bin/python tests/benchmark_incremental_refresh.py`. One run measured 7-day Overview/time cold full **1.0302 s**, one new request **0.2640 s** (`delta`, one bucket), subsequent full **1.0587 s**; hours-gap (200 rows) **0.1861 / 0.1088 / 0.1920 s**; moving 24h Overview/model (864 rows, +100s) **0.3310 / 0.2222 / 0.3257 s** (`delta`, two edge buckets). Complete projected DTO parity was asserted against full reads at each same bound. These are single local samples, not a latency promise or installed-gateway proof; dependent corrections spanning buckets may deliberately fall back. Focused fixture/route checks exercise rolling expiry and model/unknown corrections, predecessor outside scope, exact decimal/unknown counts, distinct subagents, WAL source sentinels, replacement and concurrent writer races, oversized journal payloads, rollback, missing history, tampered tokens and legacy migration opt-in. These backend-lane samples predate the later renderer integration; independent review, frontend consumption and any authorised migration were outstanding at that point.

After the backend blocker corrections, the same standalone synthetic fixture measured 7-day full/change/full **1.0883 / 0.2720 / 1.0780 s** (6,000 rows, one bucket), hours-gap **0.1907 / 0.1103 / 0.1885 s** (200 rows, one bucket), and rolling model **0.3323 / 0.2270 / 0.3328 s** (864 rows, two edge buckets). All three returned `delta` and asserted complete DTO parity against the corresponding full read. This is a new single local sample, not paired statistical evidence of a performance improvement over the earlier run or an installed latency result. The focused backend module passed **43 tests**; the final post-edit complete backend suite passed **565, 18 skipped**. The added fixture checks cover unchanged mixed response-model buckets, same-name/wrong-table trigger tampering, malformed/future migration schemas, stale backup/busy writer, encoded/decompressed token caps, exact implicit end and half-open bucket boundaries. At this backend-lane measurement point, the source was still a candidate for independent review; frontend POST consumption and live migration had not occurred.

## Frontend incremental consumption (repository-only, after backend independent review)

The packaged pane now retains a signed receipt only inside its bounded serialized Overview/time or model RAM snapshot. It revalidates connection, selected profile, all factual filters/window/view/group/page, selected inventory and analytics code revision before showing an aged cache hit or trying POST; a cache eviction, five-minute expiry or unavailable connection identity removes POST eligibility. Fixed bounds must equal the returned bounds; moving 24h samples a new `start` and advances both previously returned bounds by the identical shift, retaining the backend's fractional implicit-end width. POST uses the exact selected query with explicit `end`, returns a whole replacement DTO, and publishes only a versioned matching projection/revision/window. A rejected, invalid or unavailable POST is followed by one bounded full GET (route 404/405/501 suppresses later POSTs in that owner); a failed GET leaves the old view visibly labelled as failed. All-profile, mutable saved markers, other views and CSV remain GET-only. Changing connection/owner while an old POST is outstanding cannot publish its result. Filesystem hints remain scheduling signals, not accounting authority.

An isolated Playwright preview bridged to actual FastAPI/TestClient on disposable SQLite ledgers passed GET receipt → held POST/cache Updating → model and time rolling corrections with `delta` DTO parity against complete GET, token reject → GET, schema-unsupported and genuinely old/no-journal GET-only, connection switch/late response, group switch and full CSV. This is browser/API-fixture evidence, not an installed host, online account or gateway measurement. A one-shot 600-request synthetic bridge sample (real API JSON serialization, Playwright round-trip, renderer painting and cache serialization) measured cold GET→paint **673.90 ms**, delta POST→paint **576.18 ms**, forced full GET→paint **876.78 ms**; bridge API portions were **241.15 / 155.63 / 218.95 ms**, respectively. Different moving windows and sequential one-off conditions mean these numbers do not establish a repeatable or live speed-up. First reads, old ledgers and All profiles retain full-read cost. No automatic migration is provided: enabling the journal on an existing ledger remains an explicitly approved offline backup, writer exclusion and migration decision. **At this frontend-integration stage** independent frontend review and install/migration were still open. Focused backend regression passed **125 tests**; the 665-test backend collection was run in two non-overlapping alphabetical batches because the single invocation exceeded the 420-second tool limit: **426 passed, 18 skipped** before `test_page_hydration.py`, then **221 passed** from that module onward. Both batches completed with no failures; the single-process full suite had **not** completed at that point. Node syntax and the relevant projection, memory, connection and real-API bridge browser scripts passed. The single-process time limit was not diagnosed as a hang: individual page-hydration tests completed, and the second batch took about 251 seconds with read-performance fixture setup/parity dominating.

## Renderer cache and read-path implementation contract (repository candidate)

The packaged pane may retain completed, validated, projected `/ledger` responses **in renderer RAM only**; no storage, IndexedDB, gateway or backend cache. First entry requests only the active view (default 24h); other views load on first use. A same-identity revisit displays the saved result after cheap scope/revision checks, before the expensive full read, with its actual generation timestamp/window, age and an explicit **Updating** state while a fresh full response is read. Failure keeps the labelled old result and an error, not a false fresh/Online assertion. Cache lookup is scoped by connection, profile, provider/model, agent/project/session/subagent, bucket/window, view/group/page and the **observed** backend revision/inventory hint; saved-marker windows are not cached. A changed filter cannot borrow a differently scoped header. Cache entries have a finite count, byte and age budget; oversized responses are never admitted. Unmount does not clear the module cache; plugin disposal/hot reload clears it and invalidates late completions. A rolling period can reuse a previous result only as an explicitly aged historical window; a newer response replaces it. Change-token metadata is a cheap scheduling hint, not evidence of unchanged accounting. Periodic reconciliation, owner liveness and rolling-time refresh remain genuine reads, and CSV always obtains fresh full unprojected pages with its existing guards.

A complete transactional changed-row journal, paired snapshot/watermark, stable bounded pages and invalidation for mutable requests/compressions, project rewrites, pricing/health, owner liveness, predecessor/successor cache writes and rolling-window exits are prerequisites for **exact delta totals**. Neither `events.seq` nor filesystem metadata satisfies them. Until implemented, do not advertise a genuine incremental accounting patch: optimise independently correct full-read stages, retain honest refresh labels and state the remaining schema/product decision. Backend reads must keep exact Decimal, unknown, coverage and identity semantics; benchmark the same synthetic fixture before/after, not historical drifting windows.

The successor's renderer cache is capped at 12 projected responses, 2 MiB per response and 8 MiB estimated UTF-16 payload in total, with a five-minute TTL; these caps do not include the active React tree, JSON stringify peak or gateway process RAM. The installed SDK exposes `host.state.connectionId` and `ctx.onDispose`; older SDKs without connection identity do not cache. Before exposing a prior response, the coordinator reads `/ledger/change-token` and `/ledger/analytics` for the same scope. A changed hint on an aged same-identity cache entry is **not** an unconditional bypass: it can still show the explicitly historical/Updating entry while the genuine read runs; an unavailable hint or changed code revision bypasses it. Matching filesystem metadata does **not** certify current totals, and a reload between separate checks and display can still leave a briefly visible aged snapshot, hence the historical label and full follow-up read. Saved markers bypass cache because their factual end can change independently of the request URL. The renderer predecessor uses full reads at least every minute for rolling windows and every five minutes for static windows while visible, plus on visibility return; it does not yet call the new backend refresh route. The predecessor introduced no migration. The separately described backend successor provides a new-ledger-only journal and opt-in offline migration utility; neither is a renderer cache or an automatic existing-ledger migration.

A disposable 6,000-request fixture compared the prior source at `58177634` with a bounded 256-row TEMP-insert batch on the identical fixed fixture. Full Overview model medians (three reads each) were **1.8891 s baseline / 1.9275 s candidate**; an hours-gap window selecting 1,200 rows was **0.6027 / 0.5917 s**; after one earlier request's cache-read counter changed, **1.8477 / 1.8238 s**. Full DTOs were equal throughout. This did not establish a meaningful speed-up in the measured projection seam, so the batch experiment was **removed**. These timings are local synthetic backend reads, not installed, browser or true delta timings; no backend read-path change is claimed. Cache hit latency is instead the generation/inventory checks and renderer paint, with a full read still running afterwards. No live-ledger benchmark was repeated.

At the renderer-only predecessor stage, the repository fixture run passed **522 backend tests, 18 skipped**; Node syntax, generated-preview rebuild and focused projected-view/cache/connection/coordinator/browser layout checks passed. A sweep of **all 41 offline browser scripts** returned **29 passes, 12 failures**. Each of the same 12 failed when run against an isolated `git archive HEAD` copy of the untouched `58177634` baseline: abandoned-requests, browser, chart-interactions, filter-toolbar, JSON-inspector, named-project, pane-height, pane-sparse-allocation, provider-limits-subagent-surface, retrospective, shared-surfaces and table-ordering. Do not call the whole offline browser suite green; no baseline browser regression was identified in this sweep. The new cache-specific script measured **235.7 ms** from a synthetic cold Requests click through manually released fixture read/render, versus **152.1 ms** from revisiting Requests until the labelled cached body appeared while its read remained held (single samples including Playwright overhead, not backend/network benchmarks); its oversized-entry, count, byte-budget, TTL and disposal checks passed. Independent review was still outstanding at that stage; installed runtime verification remains outstanding. ## Evidence and root cause

The local `infra` SQLite source was 457,932,800 bytes, with a 1,705,712-byte WAL when inventoried; default was 4,579,328 bytes with no WAL. Each read-only copy was made with `read_snapshot.snapshot_root` into disposable scratch, not by opening SQLite on the source. On the baseline, sequential selected-profile reads returned 118/14,795/25,406 requests for 1h/24h/7d in 1.532/25.145/41.854 seconds respectively (30 detail rows); the copy itself took 0.322 seconds. Default had 0/0/38 rows and took 0.053/0.053/0.095 seconds. These windows were sampled at one instant; cardinality changes over time, so those timings are not a strict paired comparison.

The read projects calculated session-cache writes and scalar accounting once per selected request, but the SQL expression for `execution_state(data)` and missing-field `CASE` categories was re-evaluated inside every full-set total/group/trend. A 2,000-row disposable fixture made **34,744** `execution_state` calls for **49** open rows plus 19 paginated details (before change). Owner inspection itself was cached per connection; repeated function/JSON evaluation, not 34,744 process probes, was the defect. Closed/abandoned rows must still short-circuit without inspecting owners. For 24h of real local data after projecting owner state, stage instrumentation found 82 state evaluations, 3.108 seconds projecting session writes, 0.679 seconds scalar materialisation, 8.739 seconds attribution rollups, and 1.420 seconds applied-rate grouping, within a 20.258-second read. The later missing-reason projection reduced rollup time but did not eliminate every full-set grouping cost.

The frontend mounts only the active subpage, but before the projection candidate `useLiveLedger` still requested the full `/ledger` response for Overview. The backend eagerly built Requests detail/cache progression, up to 1,000 compression details and their auxiliary summaries, applied-rate groups, Models & tasks groups, and all attribution/trend groups. An instrumented intermediate candidate 24h read was 16.935 seconds for 14,854 requests; SQL categories included 3.459 seconds for project/session/subagent grouped summaries, 1.534 seconds for global project options, 0.955 seconds applied-rate groups and 0.961 seconds Models & tasks groups. An extra TEMP rollup-source variation was then discarded because it did not improve latency. The reviewed per-read SQL candidate's 24h read took 18.334 seconds for 14,873 requests, including 3.266 seconds session-write projection, 0.821 seconds scalar/reason materialisation, 7.764 seconds attribution rollups and 1.220 seconds applied-rate grouping. The upper summary needs full-set totals, provider groups, trend, subagent summary, compression count and filter options; lazy-mounting React alone could not remove backend work. The opt-in projection described below is a distinct, uninstalled successor to that candidate; the default endpoint remains complete.

## Candidate and verification boundary

`session_cache_writes.materialise_summary` now projects each selected open execution state and each missing-field reason once into connection-local TEMP values; every full-set rollup reuses them. The exact owner-state short circuit is shared with `storage._exprs`; detail rows are still decorated freshly and previous-session reads remain independent of selected filters. No cross-read cache, timeout increase, truncation or hidden busy state. Default `/ledger` response fields and all-profile aggregation remain unchanged.

On one **identical** 6,000-row disposable fixture, three unprofiled alternating HEAD/final-candidate runs returned the same 826 rows for 24h with medians **1.101 s → 0.463 s**, and the same 6,000 rows for 7d with medians **6.506 s → 2.177 s**. These timings are separate from instrumentation and do not predict real-ledger speed. Sequential live-copy final-candidate samples returned 99/14,874/25,485 requests for 1h/24h/7d in **1.449/17.865/29.827 seconds** (copy 0.182 seconds); windows and request counts drifted since baseline. The 7d read is still slow, and a 30d full response or multi-profile fan-in can still be slower. No authenticated end-to-end request-stage timing has been measured. If a user still sees a minute-scale delay after this candidate is installed, distinguish gateway queue/worker wait, backend read duration, payload transfer and refresh-follow-up timing with separately approved runtime observation rather than attributing all wait to the SQL projection.

The coordinator's refresh implementation checks a change token before and after a read; manual Refresh while a read is active marks it dirty and schedules a genuine follow-up after 400 ms. The active read publishes its response before the follow-up; the manual busy state remains until the follow-up settles. This can approximately double the perceived wait without a deadlock. No spinner concealment or semantic change was made. The recorder badge is a separate status check. Backend `/ledger` is a synchronous FastAPI handler backed by a read-only analytics generation; a read can occupy its worker for the measured duration, but no live worker-queue delay was established.

Fixture regression comparisons assert full response equality against the original unmaterialised SQL for selected filters/pages, marker/bucket intersection and all-profile pagination, alongside fresh owner-state counts and repeat-read liveness. The standard backend suite and independent review remain distinct gates; passing fixtures do not prove the installed plugin or browser latency.

## Opt-in active-view successor — uninstalled

`GET /ledger` without `view` retains the exact complete response (with no new manifest). Invalid views/groups return 400; `view=overview` requires one of `model`, `time`, `project`, `session`, `subagent`. Other views are `requests`, `cache`, `compressions`, `models`, `skills` and do not accept a group. A version-1 `projection` manifest names included and omitted report fields; omission is neither an empty measured set nor zero. All views keep the same-snapshot summary/provider totals/trend/subagent summary/project options/markers/compression count and scope metadata. Overview computes just the selected breakdown; Requests computes detail and cache progression; Cache computes saved applied rates and price catalog status; Compressions computes details and linked auxiliary summaries; Models & tasks computes its grouping; Skills has a separate history route and receives only the shared ledger header. All-profile fan-in merges only included data, qualifies local identities and retains coverage/unknowns. The client keys the coordinator by committed tab/group, shows an explicit pending body rather than old rows under a new label, retains only same-scope shared header values, and forces legacy full reads for frozen-window paginated CSV with sequence/coverage/catalog guards. No prefetch or cross-read result cache was added.

Sequential timings on **one** approved read-only `infra` snapshot (copy 0.158 s), same fixed 7-day bounds and **25,739** requests, 30 detail rows: full cold/repeat **30.594/30.121 s**; Overview model cold/repeat **14.521/14.470 s**; Overview project **14.921 s**; Requests **14.852 s**; Cache **14.792 s**; Compressions **12.433 s**; Models & tasks **14.697 s**; Skills header **12.217 s**. These are backend local reads on the copied ledger, not HTTP, gateway queue, browser rendering or installed runtime timings. The first call's colder state did not materially change the repeated Overview sample; this is not a claim of warm-cache effectiveness. A separate 7-day sample with 25,741 requests took **14.372 s** for Overview model; stage wrappers measured **5.200 s** session-write projection, **3.327 s** attribution/option work (including subagent summary), **1.672 s** for two scalar summaries, **1.384 s** reason/state materialisation, **0.644 s** trend and **0.436 s** legacy-view scan. Nested stage totals overlap. The largest measured remaining seam is required per-read session-write projection, not hidden tab payload. This candidate reduces backend work but does **not** make 7-day first reads near-instant or solve an unmeasured gateway queue. Do not treat `events.seq` alone as a complete delta revision: compression cascades, attribution/project rewrites, pricing/health/context updates, late usage, predecessor effects and owner/time liveness require a separately reviewed invalidation/journal design before claiming incremental correctness.

The opt-in API signature, analytics reload manager and packaged pane changed. Repository edits and preview tests do not activate either installed profile; first activation requires installing reviewed bytes to both target profiles and a user-controlled backend restart to mount the new route/manager. The remote gateway must remain running; no restart, installation, commit, push, quota/provider call or live writer was performed for these measurements. Earlier implementer fixture checks compared every projected field to the complete response for selected/all profiles including markers, effective model, empty and partial coverage; standalone Chromium checks exercised active tab/group pending and late-completion isolation, CSV and existing controls. That earlier complete backend run returned **521 passed, 18 skipped**. It is historical verification, not the later independent run.

The subsequent corrected repository candidate passed independent review of the projection/reload contract, stale-view epochs, sparse DTO and CSV handling, and Codex reset controls. The reviewer ran the complete backend suite with **522 passed, 18 skipped**, five relevant offline browser scripts, Node syntax, generated-preview parity and diff checks. Those checks establish neither new latency measurements nor installed/browser performance; the **30.594 s** full and **14.521 s** Overview figures above remain the earlier local copied-ledger observations. Installation, live provider/account effects and end-to-end gateway/browser latency remain unverified.
