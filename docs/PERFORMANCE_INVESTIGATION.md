# Period-change latency: measured read-side cost

**Scope:** `ee941c4` baseline and an uninstalled candidate. Measurements are local read-only copies of the default and `infra` usage ledgers, or disposable synthetic fixtures. They do not prove end-to-end gateway/browser latency, concurrency under load or another user's profile. The **Online** badge denotes recorder/subscription health, not a fast analytics response (`ANALYTICS_RELOAD.md`). No provider/account endpoint or live-ledger writer was called.

## Evidence and root cause

The local `infra` SQLite source was 457,932,800 bytes, with a 1,705,712-byte WAL when inventoried; default was 4,579,328 bytes with no WAL. Each read-only copy was made with `read_snapshot.snapshot_root` into disposable scratch, not by opening SQLite on the source. On the baseline, sequential selected-profile reads returned 118/14,795/25,406 requests for 1h/24h/7d in 1.532/25.145/41.854 seconds respectively (30 detail rows); the copy itself took 0.322 seconds. Default had 0/0/38 rows and took 0.053/0.053/0.095 seconds. These windows were sampled at one instant; cardinality changes over time, so those timings are not a strict paired comparison.

The read projects calculated session-cache writes and scalar accounting once per selected request, but the SQL expression for `execution_state(data)` and missing-field `CASE` categories was re-evaluated inside every full-set total/group/trend. A 2,000-row disposable fixture made **34,744** `execution_state` calls for **49** open rows plus 19 paginated details (before change). Owner inspection itself was cached per connection; repeated function/JSON evaluation, not 34,744 process probes, was the defect. Closed/abandoned rows must still short-circuit without inspecting owners. For 24h of real local data after projecting owner state, stage instrumentation found 82 state evaluations, 3.108 seconds projecting session writes, 0.679 seconds scalar materialisation, 8.739 seconds attribution rollups, and 1.420 seconds applied-rate grouping, within a 20.258-second read. The later missing-reason projection reduced rollup time but did not eliminate every full-set grouping cost.

The frontend mounts only the active subpage, but before the projection candidate `useLiveLedger` still requested the full `/ledger` response for Overview. The backend eagerly built Requests detail/cache progression, up to 1,000 compression details and their auxiliary summaries, applied-rate groups, Models & tasks groups, and all attribution/trend groups. An instrumented intermediate candidate 24h read was 16.935 seconds for 14,854 requests; SQL categories included 3.459 seconds for project/session/subagent grouped summaries, 1.534 seconds for global project options, 0.955 seconds applied-rate groups and 0.961 seconds Models & tasks groups. An extra TEMP rollup-source variation was then discarded because it did not improve latency. The reviewed per-read SQL candidate's 24h read took 18.334 seconds for 14,873 requests, including 3.266 seconds session-write projection, 0.821 seconds scalar/reason materialisation, 7.764 seconds attribution rollups and 1.220 seconds applied-rate grouping. The upper summary needs full-set totals, provider groups, trend, subagent summary, compression count and filter options; lazy-mounting React alone could not remove backend work. The opt-in projection described below is a distinct, uninstalled successor to that candidate; the default endpoint remains complete.

## Candidate and verification boundary

`session_cache_writes.materialise_summary` now projects each selected open execution state and each missing-field reason once into connection-local TEMP values; every full-set rollup reuses them. The exact owner-state short circuit is shared with `storage._exprs`; detail rows are still decorated freshly and previous-session reads remain independent of selected filters. No cross-read cache, timeout increase, truncation or hidden busy state. Default `/ledger` response fields and all-profile aggregation remain unchanged.

On one **identical** 6,000-row disposable fixture, three unprofiled alternating HEAD/final-candidate runs returned the same 826 rows for 24h with medians **1.101 s → 0.463 s**, and the same 6,000 rows for 7d with medians **6.506 s → 2.177 s**. These timings are separate from instrumentation and do not predict real-ledger speed. Sequential live-copy final-candidate samples returned 99/14,874/25,485 requests for 1h/24h/7d in **1.449/17.865/29.827 seconds** (copy 0.182 seconds); windows and request counts drifted since baseline. The 7d read is still slow, and a 30d full response or multi-profile fan-in can still be slower. No authenticated end-to-end request-stage timing has been measured. If a user still sees a minute-scale delay after this candidate is installed, distinguish gateway queue/worker wait, backend read duration, payload transfer and refresh-follow-up timing with separately approved runtime observation rather than attributing all wait to the SQL projection.

The coordinator's refresh implementation checks a change token before and after a read; manual Refresh while a read is active marks it dirty and schedules a genuine follow-up after 400 ms. The active read publishes its response before the follow-up; the manual busy state remains until the follow-up settles. This can approximately double the perceived wait without a deadlock. No spinner concealment or semantic change was made. The recorder badge is a separate status check. Backend `/ledger` is a synchronous FastAPI handler backed by a read-only analytics generation; a read can occupy its worker for the measured duration, but no live worker-queue delay was established.

Fixture regression comparisons assert full response equality against the original unmaterialised SQL for selected filters/pages, marker/bucket intersection and all-profile pagination, alongside fresh owner-state counts and repeat-read liveness. The standard backend suite and independent review remain distinct gates; passing fixtures do not prove the installed plugin or browser latency.

## Opt-in active-view successor — uninstalled

`GET /ledger` without `view` retains the exact complete response (with no new manifest). Invalid views/groups return 400; `view=overview` requires one of `model`, `time`, `project`, `session`, `subagent`. Other views are `requests`, `cache`, `compressions`, `models`, `skills` and do not accept a group. A version-1 `projection` manifest names included and omitted report fields; omission is neither an empty measured set nor zero. All views keep the same-snapshot summary/provider totals/trend/subagent summary/project options/markers/compression count and scope metadata. Overview computes just the selected breakdown; Requests computes detail and cache progression; Cache computes saved applied rates and price catalog status; Compressions computes details and linked auxiliary summaries; Models & tasks computes its grouping; Skills has a separate history route and receives only the shared ledger header. All-profile fan-in merges only included data, qualifies local identities and retains coverage/unknowns. The client keys the coordinator by committed tab/group, shows an explicit pending body rather than old rows under a new label, retains only same-scope shared header values, and forces legacy full reads for frozen-window paginated CSV with sequence/coverage/catalog guards. No prefetch or cross-read result cache was added.

Sequential timings on **one** approved read-only `infra` snapshot (copy 0.158 s), same fixed 7-day bounds and **25,739** requests, 30 detail rows: full cold/repeat **30.594/30.121 s**; Overview model cold/repeat **14.521/14.470 s**; Overview project **14.921 s**; Requests **14.852 s**; Cache **14.792 s**; Compressions **12.433 s**; Models & tasks **14.697 s**; Skills header **12.217 s**. These are backend local reads on the copied ledger, not HTTP, gateway queue, browser rendering or installed runtime timings. The first call's colder state did not materially change the repeated Overview sample; this is not a claim of warm-cache effectiveness. A separate 7-day sample with 25,741 requests took **14.372 s** for Overview model; stage wrappers measured **5.200 s** session-write projection, **3.327 s** attribution/option work (including subagent summary), **1.672 s** for two scalar summaries, **1.384 s** reason/state materialisation, **0.644 s** trend and **0.436 s** legacy-view scan. Nested stage totals overlap. The largest measured remaining seam is required per-read session-write projection, not hidden tab payload. This candidate reduces backend work but does **not** make 7-day first reads near-instant or solve an unmeasured gateway queue. Do not treat `events.seq` alone as a complete delta revision: compression cascades, attribution/project rewrites, pricing/health/context updates, late usage, predecessor effects and owner/time liveness require a separately reviewed invalidation/journal design before claiming incremental correctness.

The opt-in API signature, analytics reload manager and packaged pane changed. Repository edits and preview tests do not activate either installed profile; first activation requires installing reviewed bytes to both target profiles and a user-controlled backend restart to mount the new route/manager. The remote gateway must remain running; no restart, installation, commit, push, quota/provider call or live writer was performed for these measurements. Earlier implementer fixture checks compared every projected field to the complete response for selected/all profiles including markers, effective model, empty and partial coverage; standalone Chromium checks exercised active tab/group pending and late-completion isolation, CSV and existing controls. That earlier complete backend run returned **521 passed, 18 skipped**. It is historical verification, not the later independent run.

The subsequent corrected repository candidate passed independent review of the projection/reload contract, stale-view epochs, sparse DTO and CSV handling, and Codex reset controls. The reviewer ran the complete backend suite with **522 passed, 18 skipped**, five relevant offline browser scripts, Node syntax, generated-preview parity and diff checks. Those checks establish neither new latency measurements nor installed/browser performance; the **30.594 s** full and **14.521 s** Overview figures above remain the earlier local copied-ledger observations. Installation, live provider/account effects and end-to-end gateway/browser latency remain unverified.
