# Incremental analytics read contract (repository candidate)

This is an uninstalled repository candidate, not a live performance guarantee. Signed receipts are supported for eligible **nonpaged** selected-profile Overview time/model reads on newly created journalled ledgers; paged pane reads remain GET-only. The request-only reducer keeps its bounded-bucket rules, then recomputes every observed child peak from lifecycle events and matching request evidence in the **same copied ledger** before sealing a complete replacement DTO. Event-only lifecycle changes can therefore produce a delta with fresh peaks. Earlier signed receipts lacking peak fields fall back to a fresh full read; invalid or mismatched tokens still fail validation. Old ledgers without a supported journal remain full reads, without migration by reading. Neither version is installed or live-verified. See [offline delivery](OFFLINE_DELIVERY.md) for the gated handoff. The existing `GET /ledger` without `view`, pagination and CSV remain complete full reads. A selected-profile, positive finite `start`, optional `end`, and `view=overview&group=time|model` GET on a **newly created** ledger returns the normal projected response plus:

```ts
type IncrementalReceipt = {
  version: 1;
  revision: number;              // transactional SQLite change revision
  mode: 'snapshot' | 'delta';
  resume_token?: string;          // opaque, signed, compressed baseline; RAM only
  changed_buckets?: number;       // delta mode only
};
type OverviewResponse = ExistingOverviewTimeOrModelResponse & {
  incremental?: IncrementalReceipt; // absent on legacy/uninstrumented databases
  analytics_revision: string;       // code generation, not a data revision
};
```

For a response with `resume_token`, call `POST /ledger/refresh` with the same profile/scope/filter/page/view/group query values as `GET /ledger`, **explicitly forwarding the response's `window.start` and `window.end` as the bounds**, and JSON `{ "resume_token": "..." }`. A GET with omitted `end` resolves the actual SQL bound once and signs that exact reported end; it does not invent an end or extend the selected interval. Bounds may match exactly, or advance together by the same strictly positive amount up to 3600 seconds when the prior width is 86400–86460 seconds and the new width equals it (to 0.001 second); the small overrun admits a server-resolved implicit end after a client-sampled 24h start. No bound moves backward or widens. To roll, advance **both** reported bounds by the same shift; do not omit `end` on the POST and expect the server to resample it. The response is a **complete replacement** projected DTO, not an arithmetic client patch. Replace the old token with the new token, including on a snapshot fallback. A response without a token, saved marker, all-profile scope, unsupported view/group, backend restart (invalid token), changed profile/filter or explicit 400 must use `GET /ledger`. Do not persist tokens; they encapsulate the signed prior scoped DTO and exact bucket/provider/model contributions. They die with renderer RAM and are not a backend cache. Never mix tokens between profiles or views. The host gateway's existing authentication policy applies to both routes. The repository candidate now calls POST for eligible selected-profile Overview/time and model only; release/installation is separate.

`mode: delta` means the request/accounting reducer read only affected time buckets through the production SQL projection, while observed child peaks still require a full lifecycle-event sweep and matching child-request scan of the selected window on the same disposable copied source. It does **not** promise all-read cost proportional to changed buckets. The reducer includes the departing/entering clipped edge buckets on a rolling move and session-stream successors across filter/date boundaries. The selected source is backed up once through SQLite (including committed live WAL), then narrow reads and final distinct-membership/latest-order queries share that copied generation. Summary/provider/model/subagent values use exact per-bucket contributions; selected distinct session/agent counts and provider/model latest ordering are recomputed from the copied source. Model contributions and membership use the same **effective response-model SQL expression**, not SQLite's ambiguous `model` GROUP BY alias (which resolves to the stored request-model column). Decimal strings and unknown-field counters use the same SQL as full reads. The client need not inspect `changed_buckets`. A fresh full response (`mode: snapshot`) is normal when the journal is missing/gapped, more than 128 changes or four affected buckets occurred, an affected bucket contains more than 2048 requests, an oversized journal row exists, a writer other than requests/events changed data, projection metadata changes, an open owner needs fresh liveness, the code/source generation changed, the source changed during the copied read, or the 4 MiB **uncompressed and encoded token** budget / 2048 provider-bucket / 4096 model-bucket group budget is exceeded, or Decimal(28) reassociation cannot be proved exact for selected cost values. The decoder checks the signed packed bytes before capped decompression and rejects trailing/unfinished streams. Retrying with the returned full token is allowed. A 400 scope/token mismatch is not a usable prior result. Filesystem identity alone never proves unchanged accounting; transactional revision/DB identity and source-file generation must also match. No immutable live-WAL shortcut is used. Every selected GET/refresh POST backs up the existing `mode=ro` source in one SQLite step to disposable storage, allowing normal WAL/SHM sidecar effects but no source usage/account/ledger-row writes; active WAL writers can continue. Lock retries have the existing two-second SQLite budget and return retryable 503 when exhausted. All-profile reads retain the strict raw-file copy/no-source-SQLite-connection path. A source change during the copied read can still prevent receipt sealing or force a full refresh fallback, but cannot mix rows from two SQLite generations within one report.

Newly created `Store` ledgers get SQLite `analytics_changes` plus `analytics_change_meta` (schema version 2 with random durable DB identity) and `AFTER INSERT/UPDATE/DELETE` triggers for requests, compressions, events, session context, pricing/catalog/status, rates, tests, health, quota and skill observations. The journal retains at most **4096 mutations** and **8 MiB of payload/identity/kind bytes plus 64 bytes/row accounting**, in the same source transaction as each mutation. Request entries preserve exact old/new SQL values when each serialized row is at most **32768 bytes**; larger old or new rows produce a bounded invalidation, so refreshing through that revision requires full fallback. Non-request entries carry kind/short identity invalidation. These bounds are logical retained journal payload, **not** a cap on SQLite pages/WAL or event/request source data. This is durable source history, **not a disposable derived cache**. It duplicates recent request payloads, adds write/WAL overhead and retains database pages after logical pruning until normal SQLite maintenance. There is no TTL deletion or automatic VACUUM. Every eligible projected read compares the **complete non-internal main-schema table/index/trigger inventory** with canonical definitions (including source and journal tables/indexes and every trigger body). Extra triggers of any name, including ones on journal metadata or tracked source tables, and extra tables/indexes fail closed; names are never an authority boundary. Refresh also verifies revision continuity. A database that predates this source change is **not migrated by Store initialization or reads**; it stays on full reads until a separate operator-authorised deployment/migration. The offline function accepts only known version-0 legacy DDL and refuses future/unknown versions pending **explicit future approval**; it never auto-upgrades or guesses compatibility. An operator must stop and externally exclude all writers, take a consistent standalone SQLite backup, verify its SHA-256 independently and preserve it, review retention/write overhead and authorise an absolute nonsymlink exact target. Then, *only on that offline target*, invoke `migrate_offline(path, confirmed=True, offline_target=path, backup=backup_path, backup_sha256=verified_lowercase_hex_digest)`. The utility verifies backup hash/integrity and takes an exclusive SQLite transaction; before a first installation it also checks target integrity/schema, locked logical-content equality and every tracked `data` JSON value's readable object/nested mapping/sequence/finite-cost shape **before DDL**; malformed request, compression, context, skill or pricing records are refused with table/ordinal-only errors, never repaired or deleted. Missing optional legacy fields and unknown extra fields remain admissible. Preflight also checks every saved request rate and every catalog rate for the exact fields consumed by `accounting.costs` and `pricing.select_rate` (including finite numeric prices, model/tier, band thresholds and snapshot metadata). Empty/sparse legacy catalogs remain admissible. After equality proof it copies the verified backup into owned disposable scratch and invokes the production `Store.read` method without constructing a Store: read-only main SQLite, writable connection-local TEMP, full nonnegative request history, every 2000-row request detail page, Overview time/model and cache/model projections. The scratch copy is removed on success or failure; neither backup nor target is passed to this read. Open requests with owner objects are refused at the liveness stage rather than inspecting `/proc` or classifying a potentially live producer. This does **not** certify every possible filter, compression-detail path, historical rate/health/quota page or unrelated user-provided JSON semantics: legacy sparse compression objects may lack modern detail keys. All tracked JSON objects are parsed but only consumed rate/catalogue fields and exercised read paths have structural guarantees. Read/validation failures are payload-free table/row or reader/stage errors before any analytics DDL. It then installs atomically or rolls back. A valid already-upgraded target is a no-op after backup proof/integrity but need not match its pre-migration backup byte-for-byte. `confirmed=True` is intent, **not proof** writers stopped; the SQLite lock excludes cooperating concurrent writers during the transaction, not future writers or processes operating on a different inode. The external offline preflight remains mandatory. It was exercised only against disposable fixtures, never live. Reconciliation through raw SQLite updates is covered by the triggers when installed; pricing/context/health changes force full fallback.

The repository-candidate renderer now consumes this route for selected-profile Overview/time or model when it retains an eligible same-scope serialized RAM snapshot **without a saved marker or bucket filter**; first reads, uninstrumented/old ledgers and unsupported scopes remain GET. It samples rolling 24h `start` on each read, derives the same shift for both previously returned bounds, and forwards explicit `end`. All five selected Overview group GETs validate independently of POST eligibility, including bucket- and marker-filtered reads. Project and session breakdown attempts each partition the full summary; subagent breakdown attempts partition only the subagent summary. Before publishing or caching a POST **or corresponding selected GET**, it checks the consumed Overview header and breakdown DTO: exact version-1 projection partition when present (mandatory for POST), numeric factual window, summary field/coverage shapes, nested provider/project/test identities (nullable project provenance and open-test end remain valid), and row summaries. A filtered GET must report the intersection of outer start/end, bucket and returned saved-marker timestamps; an omitted end is resolved by the server, not guessed from the display grid. If the selected marker is absent from the returned marker facts, admission fails closed. A disjoint intersection may be zero-width: the backend then returns one zero-width zero-attempt trend row, admitted only for that empty window. Since provider, time and model attempts are complete partitions of the same filtered request set, their attempts must each sum to `summary.attempts`; a positive total with a missing entire breakdown fails. Distinct sessions, Decimal cost and known token subtotals are **not** inferred by summation across partial/unknown coverage. Zero counts, empty breakdowns at zero activity, optional null/absent marker end and unknown accounting remain valid. POST additionally requires matching analytics revision, signed receipt and exact returned window. A malformed successful POST is discarded before paint/cache admission and triggers exactly one full GET; if that GET is malformed or fails, the prior snapshot remains labelled with update failure, without a second fallback. A malformed cold GET fails closed with a readable error, no invalid paint/cache and no retry loop within the read (later scheduled/manual reads may retry). Rejected/unavailable POSTs also fall back to GET. An evicted/expired cache entry cannot authorize POST; the signed token is inside the serialized payload/byte budget and is never persisted. Frontend uses no arithmetic patch, and all-profile/CSV/other pages never POST. The source implementation is `ledger_runtime/incremental.py`, `incremental_refresh.py`, `incremental_migration.py`, `storage.py`, `analytics_reload.py`, `api.py` and `desktop/plugin.js`. Focused backend fixture tests are `tests/test_incremental_refresh.py`; the real in-process API/browser bridges are `tests/ui/test_incremental_browser.py` and `tests/ui/test_effective_window_browser.py`; separate synthetic timing probes are `tests/benchmark_incremental_refresh.py` and `tests/ui/benchmark_incremental_browser.py`. Repository-only checks do not establish installed performance or authorise migrating an existing ledger. Migration remains deferred until every writer is externally stopped and excluded; approval alone is not an offline guarantee.
