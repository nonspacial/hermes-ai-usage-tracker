# Lower record lists — repository candidate

**Status:** implemented and exercised against disposable SQLite/preview fixtures; independent review, installation and live Desktop behaviour are separate. This contract does not alter Skills/subscription history.

- Requests, Compressions, Cache & costs (applied-rate groups), Models & tasks and each Overview breakdown initially return **at most ten** lower records. **Load more** appends ten, not a replacement page. Filters, profile, provider, grouping, period and view changes start a new list. Compression type is applied at the server **before** its page/count, while the upper compression total remains full-window; the JSON export explicitly says “loaded” until the selected list is complete. Show both Load more and View all records only while `list_next_offset` identifies further matching rows; keep in-flight/error recovery controls and the separate frozen Exit action. Neither a full initial page nor a nonzero count alone proves further records. The chart and summary are always calculated across the complete selected window; Overview time's full trend remains available to the chart while `list_rows` carries only the lower table's newest-first page.
- `GET /ledger` accepts opt-in `list_mode=page|all` only with a supported projected view. Absent mode retains the existing response and CSV contract. Page mode uses `offset`/`limit` for the selected lower list and reports `list_count` and `list_next_offset`; normal pane requests use `limit=10`. Requests and compressions use SQL page bounds; selected-profile grouped result rows use SQL page bounds after full-window grouping. All-profile grouped pages scan lightweight full-window group keys and `MAX(started)` from each copied source for exact distinct counts and global recency, then hydrate only page-winning keys in each source through TEMP membership. Profile-local project/session/subagent and task identities remain qualified; provider/model/rate identities merge across profiles, including distinct rate revisions. Matching-member recency and stable original-identity ties determine order before hydration. At `limit=10`, SQL normalises structurally equal saved-rate JSON before grouping, so detailed selected-group hydration is at most ten rows per readable profile, even when raw rate key order differs. Full-window summary/trend/header SQL and all lightweight key scans still run; this is a retrieval/payload bound, **not** a measured latency or total-memory speed-up. The independent per-profile copies do **not** promise simultaneous cross-profile atomicity. Summary, chart, coverage and projection manifest retain their existing semantics.
- **View all records** is an explicit single GET using `list_mode=all`, `offset=0`, resolving the current selected window anew rather than stitching it to the first page. The same selected-profile copied SQLite snapshot, or the existing per-profile copies in one all-profile response, produces all rows and aggregates. Its generation may legitimately differ from the previously displayed page. A 20,000-record safety bound returns an explicit 400 error rather than a partial list; the renderer leaves the previous list visible on refusal. This action can be expensive and creates no durable server snapshot, temporary retention service or expiry policy. The renderer keeps the complete returned DTO frozen in RAM until Exit frozen view or scope change; ongoing recorder reads cannot change it.
- Each incremental page uses the first report's factual window and checks revision, selected sequence or all-profile sequences and coverage, window and count before appending. Reject a changed generation or invalid/overlapping page without mutating the displayed list. A rolling-window refresh naturally starts again at ten; frozen report does not. No cross-request SQLite snapshot is claimed. Normal CSV export removes `view`, `group`, `list_mode` **and** list-only `compression_kind` before independent guarded full-page reads, not this frozen-list GET. Page mode deliberately uses full GET replacement on refresh: a signed Overview/time-or-model POST has no page membership/count contract. This does not disable the backend's supported signed POST for eligible non-paged selected Overview readers; same-scope renderer-RAM cache revisits and failure retention remain available, but page-mode reads do not enjoy incremental POST latency savings.
