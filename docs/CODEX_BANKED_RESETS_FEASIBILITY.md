# Codex banked resets: dashboard feasibility

## Decision

| Capability | Feasibility in this dashboard |
|---|---|
| Display balance | **Yes, conditionally.** Codex's documented app-server `account/rateLimits/read` returns `rateLimitResetCredits.availableCount` when supplied by the service. Optional `credits` rows expose ID, type, status, grant and expiry times. `null` summary means unavailable, not zero; `credits: null` means count only; rows can be capped, so the count is authoritative. Requires an appropriately authenticated Codex app-server integration, not merely the existing quota percentage. [App-server, rate limits](https://developers.openai.com/codex/app-server#6-rate-limits-chatgpt) · [Protocol type](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/RateLimitResetCreditsSummary.ts) |
| Manual redeem button | **Yes, conditionally.** The documented app-server `account/rateLimitResetCredit/consume` accepts a non-empty, per-attempt idempotency key and optionally a credit ID from the read response; otherwise the service chooses the next credit. Outcomes include `reset`, `alreadyRedeemed`, `nothingToReset` and `noCredit`; read the limits again afterwards. A user confirmation should precede this one-time account action. Codex's interactive `/usage` menu already offers earned-reset redemption; it is not a documented headless CLI redemption command. [App-server, earned resets](https://developers.openai.com/codex/app-server#8-earned-rate-limit-resets-chatgpt) · [CLI reference](https://developers.openai.com/codex/cli/reference#view-account-usage-with-usage) |
| Automatically redeem at 429 / 0% remaining | **Not safely on that signal alone; conditional as an explicit opt-in design.** The same consumption RPC could technically be invoked by a client, but OpenAI describes banked resets as requiring the user to apply them; it does not document an automatic banked-redemption policy. A generic 429 can mean model capacity rather than depleted subscription allowance, and the dashboard's calculated 0% remaining is not proof that the account has a resettable eligible window. Corroborate account/workspace identity, a fresh server-classified reached limit and available reset, and secure explicit opt-in before considering automation; handle `nothingToReset`/`noCredit` and idempotent retries. No claim that this is an endorsed automatic workflow. [Banked-reset guidance](https://help.openai.com/en/articles/20001498-how-banked-codex-resets-work) · [App-server, rate limits and outcomes](https://developers.openai.com/codex/app-server#6-rate-limits-chatgpt) · [Codex 429 model-capacity change](https://github.com/openai/codex/commit/b79bf69af6a68d162a95af883564d9e480948e62) |

## Boundaries and local gap

- **Eligibility is offer-specific**, varying by plan, workspace, region, availability and expiry. A banked reset is a saved, one-time allowance refresh, not cash/API credits or purchased top-ups; a full reset refreshes eligible five-hour and weekly windows and changes the weekly reset date. It is consumed only if an eligible window is refreshed. Global automatic resets and purchased immediate weekly resets are different things; neither is a saved banked reset. [OpenAI banked-reset guidance](https://help.openai.com/en/articles/20001498-how-banked-codex-resets-work) · [Paid instant resets](https://help.openai.com/en/articles/20001507-paid-weekly-work-and-codex-rate-limit-resets) · [Codex pricing](https://developers.openai.com/codex/pricing)
- **Authentication:** ChatGPT subscription sign-in and API-key billing are distinct. App-server documents managed ChatGPT OAuth and experimental externally managed ChatGPT tokens; the CLI says `/usage` requires Codex service account authentication. An ordinary OpenAI API key is not a substitute for the subscriber's banked entitlement. Do not obtain tokens by scraping a web session or call backend-client/private HTTP paths directly: the documented integration surface here is the local Codex app-server protocol, not a public OpenAI REST reset API. [Codex authentication](https://developers.openai.com/codex/auth) · [App-server authentication modes](https://developers.openai.com/codex/app-server#authentication-modes) · [CLI `/usage`](https://developers.openai.com/codex/cli/reference#view-account-usage-with-usage)
- **This repository does not expose a typed banked-reset control:** `dashboard/plugin_api.py`'s `_probe_standard` delegates to Hermes `agent.account_usage.fetch_account_usage`; `_serialize_snapshot` exposes availability, source, title, plan, usage windows, details, reason and fetch time, but no structured banked-reset count/details or redemption route. Hermes can include the banked-reset count in human-readable quota detail text when available; this is visible information, not a typed, selected-account-bound balance or an eligibility/consume contract. Do not parse the text to authorise a redemption. This is an integration gap, not evidence that OpenAI lacks a count. [Local source](../dashboard/plugin_api.py) (lines 292–321).

**Evidence limits of the original feasibility research:** This section used documentation/public sources only; no subscriber account, credential, app-server instance, redemption or live response was inspected. Availability and eligibility for this user's account, account-specific expiry, app-server deployment/credential fit and whether automation is permitted under the applicable terms remain unverified. The Help Centre pages were discoverable in OpenAI-indexed search results but direct browser retrieval presented a challenge; the app-server and CLI Markdown documentation and public protocol type were retrieved directly. The later source/schema audit below remains offline; it did not activate banked-reset product code.

## Banked-reset **History** (distinct from Available)

**Conclusion for an Available/History prototype:** The **Available** tab can conditionally use the documented `account/rateLimits/read` count and optional *available* credit rows as described above. A provider-authoritative **History** tab is **not established through the documented app-server protocol**. Do not populate it by relabeling available credits, token-activity `account/usage/read`, conversation history, or a local redemption log; those are not a grant/redemption/expiry ledger. The user's observed ChatGPT Resets → History UI is evidence of a product surface, but this public-source review could not establish its history request or contract. A truthful prototype should show History as unsupported/unverified (or omit the tab), not show an empty history as though the provider returned one. ## Implementation audit: supported integration blocker

This section records a **local, read-only source/protocol audit**, not account eligibility or a working product integration. The installed `codex-cli 0.155.1` generated v2 schemas in profile-owned scratch without launching an app-server or making an authenticated request. They confirm `account/rateLimits/read`, `account/rateLimitResetCredit/consume` (`idempotencyKey`, optional `creditId`; outcomes `reset`, `nothingToReset`, `noCredit`, `alreadyRedeemed`), `account/read`, `account/rateLimits/updated`, and a typed `error` notification whose `codexErrorInfo` can distinguish `usageLimitExceeded` from `rateLimitExceeded`. The limits response has optional `accountId` and `ordinaryUsageAllowed`; the snapshot windows expose **integer** `usedPercent`, so 100% by itself cannot safely distinguish an exactly exhausted allowance from a rounded value. Sparse rate-limit updates explicitly require a full read or merge, not treating absent values as zero. These are protocol capabilities, not evidence of a connected, same-account Hermes integration.

**Blocker for the approved end-to-end control under the plugin-only/no-token-bridge boundary:** The dashboard's Codex quota path calls Hermes `agent.account_usage.fetch_account_usage` (`dashboard/plugin_api.py`, `_probe_standard`), serialises a window/description DTO (including possible human-readable banked-count detail text) and does not expose a typed balance, an app-server session or its authenticated account identity. Hermes' own quota credential resolver can select a pool credential with **no account ID** (`agent/account_usage.py`, `_resolve_codex_usage_credentials`); the app-server uses its separately managed Codex login. Thus a second plugin-owned app-server process could return or redeem a *different account* from the selected Hermes profile, and an `accountId: null` response cannot prove equality. The desktop plugin's selected-profile storage and detail text are not an account-authority binding. Do not use a global Codex home, a token copy/bridge, a pool-account guess or the host's direct private consume helper to paper over this mismatch.

The automatic trigger is also absent at the plugin boundary: the current recorder persists `error_class` and optional HTTP `status_code`, not a provider-classified usage-limit notification (`ledger_runtime/recorder.py`, `error`); its health contract explicitly excludes the separate app-server runtime. Hermes' `CodexAppServerSession` consumes turn notifications inside its private per-agent subprocess (`agent/transports/codex_app_server_session.py`, `_absorb_notification` and `_drive_turn`); `make_codex_app_server_event_bridge` forwards only item/delta display events, not typed `error` or account-limit events (`agent/codex_runtime.py`). `host.onEvent` in the Desktop SDK exposes gateway events, not that raw Codex wire. Starting a dashboard-only app-server does not subscribe it to existing agent turns, and opening/polling the view is **not** a confirmed usage-limit notification. A generic 429 or rounded quota cannot replace this signal.

**Required supported prerequisite:** an authorised, account-bound host integration must expose a typed, profile/account-scoped Codex balance/eligibility reader and one idempotent consume operation against the **same** authenticated account, plus a typed usage-limit notification from the active Codex turn to the plugin (or a trusted backend handler), with stable event identity for deduplication. It must define the selected profile versus active turn/account relationship, including pool-only credentials and absent account IDs. That requires a host-core integration or a separately approved secure authentication/event contract beyond this repository's plugin-only scope. No plugin UI, redemption route, automatic opt-in, install or restart was activated by this audit; the throwaway HTML remains a simulation. Manual redemption could be investigated separately, but should not be presented in the two cards as working while the account-binding prerequisite is unmet. No interrupted-request auto-resumption is established.
