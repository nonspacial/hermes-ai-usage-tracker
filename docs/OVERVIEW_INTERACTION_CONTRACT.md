## Peak observed subagents (repository candidate; synthetic checks only)

- `subagent_start`/`subagent_stop` event timestamps are paired by child session in durable event **sequence** order (not timestamp order); clock-shifted pairs with non-positive timestamp length are rejected after pairing. Strictly positive matched half-open intervals count. An unmatched stop, duplicate/overlapping start or non-positive pair is excluded; `unmatched` counts **each** excluded recorded notification, including every start and stop of a rejected ambiguous/non-positive pair. Repeated sequential child sessions can share an agent identity, but concurrent intervals with the same identity count once. A carried-in lifetime intersects the selected factual window even if its start precedes that window. Main agents never count.
- **Open children (implementer-verified, synthetic checks only).** A single start with no later stop for its child session is bounded by evidence, never by the report boundary, in `observed_peak.bound_open`, once per read: (a) when the child's most recent recorded request (same `session_id`) has an owner that `ownership.inspect_owner` reports `live`, it runs until the read's `now` (**running**); (b) when it has requests but no live owner (dead, replaced or unknown), it ends at its latest recorded request activity (max `started`/`ended`; **open_ended**); (c) with no recorded request, it runs until `now` only if its start is younger than `OPEN_CHILD_GRACE_SECONDS` (120 s) and its start event's parent session's latest request owner is live; otherwise it is excluded. An open interval that would be non-positive is excluded. Owner inspection is cached per distinct owner per read (at most one per child). Excluded open starts stay in `unmatched`; counted ones do not.
- `peak_observed.value` is the maximum number of distinct child identities simultaneously present in counted intervals (matched, running and open-ended) intersecting `[window.start, window.end)`, not the maximum true concurrency. Additive `running` and `open_ended` give the distinct child identities of each open kind intersecting that window (older responses lack them; the pane accepts both). `null` means no counted lifecycle evidence (unknown), whereas `0` is an observed zero in a window with counted lifecycle evidence elsewhere. `unmatched` counts excluded lifecycle notifications across the readable snapshot, not missing notifications that were never recorded. Missing hooks and incomplete coverage can undercount. Caveats: a child whose stop was lost while its owner process (for example a long-lived gateway) keeps running counts as running until that process ends; an open-ended child's end is its last recorded request, which can precede its actual end. Request start/end bounds an open child only as described; it never replaces a recorded stop.
- The unfiltered period and trend buckets include counted lifetimes (matched, running, open-ended) regardless of request rows in the window. Provider, effective-response-model, project and root-session group values are attributed only where a matching child-session request was recorded in the selected request window; a scoped request filter likewise requires recorded matching evidence. These scoped peaks are **request-attributed observations**, not independently identified lifecycle provider/model facts. Groups with no evidence do not inherit an unfiltered peak. The selected period's peak is independent of lower-list pagination. All-profile period, provider/model and bucket peaks sweep the union of profile-qualified intervals, never the sum of per-profile peaks. Sources are independent snapshots and partial/missing profile coverage remains qualified.
- Placement: the graph's selected-point accent tooltip footer contains the bucket peak; provider rows beside the graph and the Subagent tokens card contain period/provider peak; Model, time, Project and Session breakdowns display their own scoped peaks under the column header `Peak subagents` (this section heading keeps its older name because other docs link its anchor). Do not add a vacuous per-subagent column. The compact tooltip leads with `Peak subagents: N` and puts one point per line: what it counts, excluded unmatched/ambiguous runs with the unmatched count, then plain `N still running` when `running` > 0 and `N ended without a stop record (counted until their last request)` when `open_ended` > 0 (the counting line then drops its `only`; the chart footer adds the same two lines after its peak line), then muted caveats for missing hooks (an undercount), request-derived grouping and non-simultaneous profile snapshots. Retain existing theme tokens and chart/tooltip interaction.
- Signed nonpaged selected-profile Overview/time or model GET receipts are supported on new journalled ledgers; POST keeps the request-only bounded reducer and recomputes all observed peaks (including open-child bounds against that read's `now` and fresh owner liveness) from the same copied snapshot before returning/sealing a delta, so a delta never carries a stale running count. Event-only lifecycle changes are observed, while old signed receipts lacking peak fields fall back to a full read; receipts with peak fields but without `running`/`open_ended` gain them on the recomputed delta. The pane's rolling-expiry skip is forbidden while the summary `peak_observed.running` is present and not 0, because liveness and `now` change without a ledger write. All-profile fan-in unions the per-profile counted intervals; its `running`/`open_ended` split needs the stable `observed_peak` import that `aggregate.py` uses, so after a hot analytics reload without a backend restart the all-profile values are already correct but may lack the split until the backend restarts. Paged pane reads remain GET-only, and old ledgers remain full reads. Renderer cache entries still require exact scope/generation and retain their age/Updating labels. A synthetic check counts one lifecycle pairing pass per delta with multiple affected request buckets; this is not a live speed guarantee.
