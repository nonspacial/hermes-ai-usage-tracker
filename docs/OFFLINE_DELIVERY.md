# Offline two-profile delivery (operator runbook)

**Not executed.** The accepted source is an uninstalled candidate, not a measured live speed-up. This procedure is for a later, externally quiesced maintenance window; do not run it from an active Hermes conversation. The target homes are exactly `/home/nope/.hermes` (default) and `/home/nope/.hermes/profiles/infra` (infra); their respective databases are `/home/nope/.hermes/usage-ledger/events.sqlite3` and `/home/nope/.hermes/profiles/infra/usage-ledger/events.sqlite3`. Neither installation nor a backend analytics reload migrates an existing ledger. Do not use `--all-profiles`. Record the full accepted commit SHA from Git at handoff; do not use a moving branch or a dirty checkout for installation.

1. **Externally quiesce both targets.** Stop and prevent *new* starts of every producer/writer for **both** profiles: desktop/backend, gateway, CLI/agent jobs, workers and any other process writing either ledger. Do not restart anything to perform this stop from this conversation. Inspect the actual process supervisor and open file descriptors for each exact DB and its `-wal`, `-shm` and `-journal` sidecars; require **no active writer or open descriptors** and no process able to reopen either target while the window lasts. Record process inventory, paths/inodes, sidecar disposition and prevention-of-restart evidence. A single SQLite exclusive lock or `confirmed=True` is not that proof. If stop/new-start exclusion cannot be proved, **do not back up/migrate/install**; keep both on their original schema and full reads. Do not delete sidecars to make a check pass.
2. **Back up separately before migration.** With writers excluded, create one consistent, standalone SQLite backup of each exact DB, using SQLite's backup API or an equivalent consistent backup that includes any committed WAL state; never use a bare copy of the main file if WAL exists. Use two distinct regular files at absolute nonsymlink paths outside the target DBs, preserve them and record which profile/inode each came from. Require no backup `-wal` or `-journal` sidecar. Independently calculate and record each backup's **lowercase 64-character SHA-256** (`sha256sum`), verify each `PRAGMA integrity_check` returns `ok`, and perform a separate **scratch restore check** for each backup: restore into a disposable, isolated DB, open it and check integrity and the expected schema/record counts against the source backup. Keep the original backups unchanged; recheck their digests just before migration. This is a manual proof gate, not an invitation to inspect live ledger contents here. If a source already has an analytics schema or malformed/unknown legacy data, investigate the exact target rather than forcing an upgrade.
3. **Migrate only while exclusion persists.** From a clean checkout pinned to the accepted commit, with project dependencies available in an isolated interpreter, call the source function separately for the default and infra DB (substitute the **independently verified** backup paths/digests, not the target path as backup):

   ```python
   from pathlib import Path
   from ledger_runtime.incremental_migration import migrate_offline
   database = Path('/home/nope/.hermes/usage-ledger/events.sqlite3')
   migrate_offline(database, confirmed=True, offline_target=database,
                   backup=Path('<absolute default standalone backup>'),
                   backup_sha256='<verified lowercase default SHA-256>')
   database = Path('/home/nope/.hermes/profiles/infra/usage-ledger/events.sqlite3')
   migrate_offline(database, confirmed=True, offline_target=database,
                   backup=Path('<absolute infra standalone backup>'),
                   backup_sha256='<verified lowercase infra SHA-256>')
   ```

   The function checks exact nonsymlink paths, backup digest/integrity, exclusive target lock, known legacy schema, locked logical equality, tracked JSON/prices and a disposable-backup production-reader preflight **before DDL**. It rolls back on failure; `confirmed=True` expresses operator intent only. Stop on any exception or mismatch and keep the writer exclusion in force while diagnosing. Do not attempt a future/partial-schema upgrade or edit ledger rows to make it pass. Migration of one target does not certify the other. Confirm each target's post-migration integrity and canonical journal/schema support with the **pinned** source, without opening the live DB from this handoff; preserve the pre-migration backups and both observations.
4. **Install pinned bytes only after both migration gates.** Independently verify `git rev-parse HEAD` is the recorded full accepted SHA and `git status --porcelain` is empty in the source checkout. From that checkout, preview and then apply exactly these source-supported installer commands (no `HERMES_HOME` inference):

   ```sh
   python3 install.py --home /home/nope/.hermes
   python3 install.py --home /home/nope/.hermes/profiles/infra
   python3 install.py --home /home/nope/.hermes --apply
   python3 install.py --home /home/nope/.hermes/profiles/infra --apply
   ```

   Preserve **both distinct** `usage-ledger-backups/.../receipt.json` paths printed by `install.py` (these are plugin-file rollback receipts, **not** the SQLite backups). For each receipt require `status=installed`, exact `home`, exact installer `plan(home)` path membership and installed file digests equal to **both** `installed_sha256` in that receipt and the matching bytes of the pinned Git checkout. Also verify the receipt's saved old-file checksums before relying on plugin rollback. Stop on any discrepancy; do not restart or report installation complete based on installer exit alone. The installer includes `dashboard/`, `desktop/`, `ledger_runtime/` and its root file allowlist, plus the desktop entrypoint; it does not change credentials/config, enable plugins or restart processes.
5. **Release and read back under user control.** Only after both migrations and installed-byte/receipt checks, the owner chooses when to re-enable starts and restart the desktop/backend **and each intended existing producer** so the startup-pinned API/schema and recorder load together. Confirm the plugin is enabled in each intended profile without changing account policy, read back mounted route/revision and selected-profile projected responses, and compare a fresh full GET with an eligible fixed or rolling Overview/time **or model** refresh for exact DTO parity, revision, bounds and fallback behaviour. Check default and infra separately, then read-only All profiles, old/unsupported views and CSV. Use the supported authenticated host UI and approved observation, not a provider/quota action or a fabricated ledger write. Observe gateway queue/read/transfer/paint timing separately before making a performance claim; Online is not proof of fast analytics. Installation, restart, real ledgers and live performance have **not** been verified by repository fixtures.

**Rollback boundary:** Before *any* post-migration writes, while all writers remain excluded, an operator may restore each preserved, verified SQLite backup as a **whole database state**, reconciling/removing its WAL/SHM/journal sidecars safely under SQLite semantics, then verify integrity and its original schema before restarting. Do not overlay a live DB main file or silently discard committed WAL. If either ledger has received **any** post-migration write, restoring the pre-migration backup loses that history: stop and obtain a separate reconciliation decision, not an automatic rollback. Preview `python3 install.py --rollback <that profile's receipt.json>` then apply `python3 install.py --rollback <that profile's receipt.json> --apply` only after its destination and saved-file checks pass; do so separately for both profiles. Plugin-file rollback does **not** reverse ledger migration. Restart/re-enable producers only by owner decision after both plugin/database states are coherent.
