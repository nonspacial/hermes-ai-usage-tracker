# Ledger runtime DOX

## Purpose

Own event recording, SQLite storage, request accounting, pricing, analytics reads and multi-profile aggregation.

## Ownership

`recorder.py` and adapters observe producer events; `storage.py` owns durable records and report reads; `aggregate.py` combines read-only profile reports; `api.py` exposes scoped ledger routes; `skills.py` owns skill/context observations. Other sibling modules own the named accounting, pricing, reset and analytics-reload boundaries. Root references provide technical detail, not replacement runtime authority.

- `codex_resets.py` redemption authority (owner-private `codex-reset-authority/state.sqlite3`, `journal_mode=delete`, so a reader's SHARED lock also delays a COMMIT): observe, opt-in and admission use `BEGIN IMMEDIATE` with a `BUSY_SECONDS` (1 s) busy budget; admission still admits exactly one attempt per account and commits it (plus an `attempts` row) before the irreversible consume RPC. After a definite consume outcome (`reset`/`alreadyRedeemed`/`nothingToReset`/`noCredit`) the outcome is first journalled to `outcome-<attempt>` in the authority folder (O_EXCL, 0600, short writes completed, file and directory fsynced; body: hashed account key, attempt id, outcome), outside SQLite's lock; `_write_outcome` returns not written / written (durability unconfirmed) / durable, and `Unrecorded` says "will be", "may be" or "stays blocked" accordingly; then, after the limits read-back, `_finalise` records it with its own bounded budget (`FINALISE_SECONDS` 5 s of ≤1 s `BEGIN IMMEDIATE` tries with 50/250 ms backoff, at most `FINALISE_MAX_TRIES`), re-verifying the attempt id on every try. Recording is idempotent per attempt (`attempts.outcome`), so a racing reconciler and the finaliser never record twice. If it still cannot record (or the read-back fails) it raises `Unrecorded` (an `Unavailable`, HTTP 409) with a distinct message, never "Another redemption is in progress."; the row stays pending. Every later `observe()`, `set_auto()` or admission for that account reconciles a pending attempt whose journal is a single-link owner-private regular file matching its account key and attempt id with a known outcome: it records that outcome, clears the attempt, and deletes the journal; the episode stays spent, so the consume is never repeated, and `observe()` keeps `redeemable` false while the provider still reports that episode. A successful finalisation always deletes its journal file. Observe and admission also sweep (bounded to `SWEEP_LIMIT` `outcome-*` candidates, inside their write transaction) `outcome-*` journals of attempts no account holds pending, and prune (under `SAVEPOINT housekeep`) that account's settled `attempts` rows beyond the newest `ATTEMPTS_KEEP` (200), never the current attempt. Filesystem errors are ignored; a SQLite error is ignored only while the caller's transaction is still open — if SQLite auto-rolled it back (FULL/IOERR/NOMEM/BUSY) the error is re-raised, so admission refuses and observe fails with nothing written outside the lock. Admission maps an `OperationalError` to HTTP 409: lock contention (BUSY/LOCKED, "database is locked"/"busy") reads "Another redemption is in progress.", any other SQLite fault "Codex reset state could not be written; nothing was spent."; other `DatabaseError`s surface as 503. A pending attempt with no valid journal (crash between RPC and journal, uncertain RPC, or a pre-upgrade row) is never assigned an outcome: it stays blocked and reads `last_outcome: 'unrecorded'` once no live redeem can still record it (`INFLIGHT_SECONDS`, or immediately after an uncertain RPC; wall-clock time only moves that label, never the block). There is no in-product clear for it (unchanged; manual recovery note in the ticket, clear action an open follow-up in [docs DOX](../docs/AGENTS.md)). The desktop redeem/Auto use requests use a 60 s `timeoutMs`. Schema changes are additive only: `CREATE TABLE IF NOT EXISTS attempts` on every open; `state`/`optin` shapes and old rows are unchanged, with no offline migration.

- Writer path (producer hot path) records identical rows, events, journal entries and ordering; only overhead differs. Keep `tests/test_writer_path.py` parity against the pre-change recorder green.
  - **Connection lifecycle:** recorder `store()` instances set `Store.persistent`; `db()` then reuses one write connection per Store (one commit per checkout as before; connect/PRAGMA/close saved). Its lock is taken non-blocking: a re-entrant or concurrent checkout (other hook threads, heartbeat) opens a fresh per-call connection instead of sharing a transaction. Checkout end closes every cursor it created (no stale WAL read snapshot), and the handle is discarded and reopened after any error, a pending transaction, TEMP objects left by `read()`, a replaced/removed file (dev/inode) or a fork. Fork handlers also re-create the module locks (`storage.LOCK`, `_WRITERS_LOCK`, `_NOTIFY_LOCK`, the settle-retry condition, `recorder._LOCK`) so a child cannot inherit one held by another parent thread. `atexit` closes the handles; writes after that use fresh connections. Commits are durable before `db()` returns, so exit adds no durability. Non-recorder Store users (API/dashboard/tests) keep fresh connections; read snapshots (backup/`mode=ro`) are unaffected.
  - **At rest (WAL settle):** between hooks the ledger looks as it did with close-after-every-write: every commit is in the main file and `events.sqlite3-wal` is empty (0 bytes). A unit of work is the outermost producer hook (`hook_scope`; pre/post bursts within it share one handle; its unit ends even if resetting the hook's context variables raises, so `_units` never sticks) or a checkout outside a hook (fresh-connection fallbacks included); bursts within a turn share one connection. When the last in-process unit of a persistent Store ends, it runs `PRAGMA wal_checkpoint(TRUNCATE)` — so, like the former "last close checkpoints", concurrent hook threads never checkpoint under each other. The settle never waits on a hook thread (`busy_timeout=0`); one blocked by another connection (a reader on an old snapshot, another process writing) is retried by one daemon thread per process every `SETTLE_RETRY_SECONDS` (1 s, waiting up to `SETTLE_RETRY_WAIT_MS` each, at most `SETTLE_RETRIES` times, skipped while a unit is in progress), and the next unit settles again anyway. The settled handle then stays open only for the rest of the burst: once unused for `IDLE_SECONDS` (1 s) the same daemon thread checkpoints and closes it, so at rest there is no open handle and, as with per-write close, no `-wal`/`-shm` sidecar (deleting sidecars *within* that second, while the handle is open, is not supported, as it never was during a write). Hence a main-file-only copy taken between hooks is complete, and replacing the main file under a live producer (without `close_writer()`) is a clean rollback: fresh readers and the reconnected handle see only the replaced file and nothing stale is replayed. Replacement *during* a hook or while a blocked settle is pending is not covered — stop producers before restoring, as the delivery runbook requires. The at-rest guarantee is bounded: a reader holding one snapshot for longer than the retry budget (`SETTLE_RETRIES` × (`SETTLE_RETRY_SECONDS` + up to `SETTLE_RETRY_WAIT_MS`) ≈ 30–60 s) leaves the WAL unsettled until the next unit settles it; under a near-continuous reader the WAL was measured to peak at ≈15–19 MB before returning to 0 bytes. The checkpoint is the main remaining hook cost. Synthetic back-to-back burst on a loaded host (handle still open): ≈39 ms median per pre+post pair vs ≈22 ms without the checkpoint at d005e62 and ≈240–350 ms at 93f5475. A hook after ≥1 s idle also pays a reconnect, since the idle close has dropped the handle (≈70 ms measured).
  - **Durability:** `synchronous=FULL` stays the default. `HERMES_USAGE_LEDGER_SYNCHRONOUS=NORMAL` (case-insensitive; any other value = FULL) is an explicit opt-in: in WAL mode it stays consistent and crash-safe for the process, but the most recent commits can be lost on OS crash or power loss. Do not make it the default.
  - **Health cadence:** the pane (`desktop/plugin.js`, `connection.status`) reads `health.updated`/`heartbeat_at` against `LEASE_SECONDS`; the heartbeat thread writes every `HEARTBEAT_SECONDS` (forced). Hooks write health only when the row content other than `heartbeat_at` changed (registration, pid, adapters, failures, last failure) or the last write for that profile is at least `HEARTBEAT_SECONDS` old, so the lease never ages more than it did between heartbeats. Content per write is unchanged. Consequently the incremental journal (`analytics_changes`) is identical row-for-row and in order **except `kind='health'`**, which has fewer entries by design (one per health write actually made).
  - **Journal trim:** new ledgers keep a one-row `analytics_change_bytes` running total, maintained by `analytics_journal_bytes_{insert,update,delete}` triggers on `analytics_changes`; the byte trim runs only when the total exceeds `MAX_JOURNAL_BYTES` and drops the same oldest prefix as the original suffix window sum (row cap unchanged). Ledgers journalled with the original window-sum triggers remain supported as-is and are never rewritten; `incremental.supported()` accepts exactly one complete generation (`LEGACY_TRIGGERS` without the table, or `TRIGGERS` with it and exactly one integer total), never a mix. The 93f5475-era `supported()` does not know the running-total generation: after a plugin rollback it takes full reads on ledgers created by this form (writes stay correct); see [offline delivery](../docs/OFFLINE_DELIVERY.md).
  - **Notify:** `notify()` sends to every listed `notify-*.sock` on every write. The listing is cached per folder while its mtime is unchanged and settled (≥`NOTIFY_SETTLE` s old at listing), at most `NOTIFY_REGLOB` s; any ENOENT/ECONNREFUSED drops the cache. Worst case, a newly bound listener misses hints for up to `NOTIFY_REGLOB` (5 s) after binding (e.g. a coarse-mtime filesystem where its bind did not change the cached mtime); it never loses records, only the prompt refresh. A refused socket is unlinked only when the PID in `notify-<pid>-<hex>.sock` is dead.
  - **Projects:** one hook reads `projects.db` once per profile (`storage.hook_scope`/`projects_for`); outside a hook every call reads afresh.
